3 · 設計方法

3.0 從零設計這套測試的五步

  1. 先定基線，不先寫用例：把「原系統行為、四輪改造決策、代碼不變量」整理成可引用的需求編號（本文件 R-01～R-12）。沒有基線的斷言，最後都會變成爭論。
  2. 先測權限，再測功能：4 角色 × 38 實體 × 6 層（菜單/直鏈/列表/表單/動作/回收桶）先跑一遍。權限錯了，後面的功能測試資料都不可信。
  3. 畫主鏈與狀態機：報價→PO→合約→發票→收據、PO→DN→庫存、盤點→沖銷，總共 5 條；每條邊至少一條用例，非法邊也要測。
  4. 每條用例寫死判定：HTTP 狀態 + DB 欄位 + 副作用 + 冪等，四層都要有；只看「頁面提示成功」不算過。
  5. 固化與閉環：把可重複的 115 項做成腳本，用例清單導出 CSV 當進度表，失敗項開缺陷單，修完追加永久用例，不刪舊例。

5 · 環境與測試數據

5.1 隔離原則（硬性）

  • 絕不在 :3000 正式庫上跑寫入測試。測試只允許在 :3101/:3102 的副本跑，DB 路徑必須在 _run_* 下。
  • 用 VACUUM INTO 做一致性快照（自動包含 WAL 已提交資料）；不要直接複製 db+wal，生產正在寫入時會得到半舊快照。
  • 每次執行用唯一 runId 前綴（如 QA-mvnt…），所有測試資料可反查、可清理，不與正式資料撞名。
  • 測試帳號只用 /demo?as= 的四個示範用戶；CPC_DEMO=1、CPC_AUTO_IMPORT=0。
# 1) 一致性快照（自動；等價於 sqlite3 .backup）
node -e "const{DatabaseSync}=require('node:sqlite');const d=new DatabaseSync('data.db',{readOnly:true});d.exec("VACUUM INTO '_run_xxxx/data.db'")"
# 若快照失敗，纔回退複製 data.db + data.db-wal

# 2) 起隔離服務
set PORT=3102
set DB_PATH=...\_run_xxxx\data.db
set CPC_UPLOAD_DIR=...\_run_xxxx\uploads
set CPC_DEMO=1
set CPC_AUTO_IMPORT=0
node server.mjs

# 3) 跑驗收（自動完成複製、啟動、清理）
node run-tests.mjs --port 3102 --keep

6 · 判定規則與缺陷管理

6.1 一條用例算「通過」的條件

層面必須同時滿足
HTTP狀態碼符合預期（成功 302/200，校驗 400，越權 403，不存在 404，衝突 409）
資料DB 欄位值與計算結果符合預期（不是隻看頁面提示）
副作用該變的變了（庫存/餘額/狀態），不該變的沒變（其他欄位、其他實體、筆數）
可重複同一用例連跑 3 次結果一致；重複提交不產生第二筆（冪等）
證據失敗必須附：請求、狀態碼、回應片段、DB 查詢結果、runId；口頭描述不算

6.2 缺陷等級

等級定義例子（本輪）處理
S1資料損壞、金額/庫存錯誤、越權可寫、核心鏈中斷刪除已過賬盤點把庫存沖成 0立即修，修完重跑全套

9 · 業務鏈與狀態機

C1 · 銷售主鏈

線索 Lead→報價 Quotation→採購單 PO→合約 Contract→排班 Schedule→服務報告 WorkRecord→發票 Invoice→收據 Receipt

驗收要點：每一步外鍵與金額可反查；任一步刪除不破壞上下游

C2 · 產品交付鏈

報價（產品）→PO→送貨單 DN→庫存扣減→發票

驗收要點：送達才扣庫存；重複送達不重扣；明細鎖定

C3 · 庫存盤點鏈

產品→庫存調整→盤點單→自動調整→回收桶

驗收要點：完成過賬、刪除沖銷、還原重過賬，三步數量閉環

C4 · 前線作業鏈

我的工作→打卡→補給→請假→服務報告（唯讀）

驗收要點：只能為本人建檔；不能審批；不能看金額

C5 · 財務結算鏈

發票→收款→收據→應收臺賬→總帳

驗收要點：餘額=總額−已付；借貸平衡；作廢不計入應收

9.1 關鍵狀態遷移

報價：已報價→跟進中→已收PO→已成交已取消/失敗
發票：草稿→已發出→部分付款→已付款逾期/已作廢
盤點：進行中→已完成（過賬）→刪除（沖銷）→還原（重過賬）永久刪除

每個箭頭至少一條用例；非法箭頭（如草稿直接已付款、未過賬直接沖銷）必須被拒絕或有明確提示。

現象為什麼可能不是缺陷建議
合約編號沿用報價編號（SQP-…）報價成交後直接成為合約號，符合部分清潔行業習慣由業務確認；若確認，寫入需求基線，測試不再斷言 C- 前綴
PO / 合約 / 收據編號欄位 required，留空被拒編號可能由客戶或人工提供，自動編號只是預留能力確認是否需要自動；若需要，required 與 defaultNumber 的順序要調整
公告頁全員可直鏈讀取，但菜單只給管理層公告本質是全員可讀，管理頁只是管理入口在權限矩陣標註「可讀」；若要嚴格，改菜單或改路由
送貨單刪除後不反向沖銷庫存可能要求人工盤點修正，避免自動回滾造成二次錯誤補需求說明；若需沖銷，按盤點模式加 stock_reversed

12.2 尚未自動化的高價值手工項

  • 列印版面（報價/發票/收據/排班/工程滿意紙）A4 斷頁與中文換行。
  • Picker 手感：50 筆清單捲動、彈窗內裁切、選中回填 ID/單位。
  • 1366×768 十二欄表格、操作列黏性、水平溢出。
  • 併發寫入（兩個會話同時保存排班/報價）與 SQLITE_BUSY 重試。
  • 辦公室每日 10 條回收桶上限與管理層通知（需構造 11 條）。
  • 公開分享連結的枚舉與過期策略（token 強度、重放）。
