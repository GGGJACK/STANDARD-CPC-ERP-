一 · 与蓝图的四处实质偏离

蓝图画的是 PostgreSQL + Next.js + RLS 的路线，实际交付是零依赖 Node + SQLite 单表。技术选型偏离本身不算错 —— 但如果偏离的同时把蓝图里"必须有"的能力也丢了，那就是问题。逐条对照如下。

蓝图要求实际实现判定影响
权限写在数据库层
「字段在出库时就已经是 NULL，前端拿到的响应里根本没有这个数字」		 权限判据分散在三处：viewRoles/editRoles（角色）、accessible_pages（页面白名单）、ownsRecord()（姓名匹配）。字段屏蔽发生在 renderValue()，即 HTML 渲染那一刻。 偏离 数据本身没有被裁剪。任何不走 renderValue 的出口（编辑表单、picker API）都会原样吐出金额。已复现，见 §2.2。
排班必须拆 schedule_employees 关联表
「否则你的第一条权限规则就实现不了」		 库里 schedule_employees 表已建好、973 行数据在，但应用层完全没读它 —— 仍在读 records 里 assigned_employees 的 JSON 数组，并用员工姓名字符串判断"这条是不是我的"。 偏离 表建了没接线，等于蓝图这一条只完成一半。姓名匹配遇到同名/改名会直接失效，见 §3.2。
办公室：客户/产品
限时 + 每日 50 次 + 静默拦截		 只对 customers 的详情页做了时间窗 + 配额（customerOfficeAccess）。产品完全没有；列表页的配额漏口靠 decorateRow() 打码补。 部分 配额只管"点进去"，而 /api/pick 可以批量拉全表，配额机制被旁路。见 §2.1。
报价 → 发票 转换链 转 PO、转合约都有 existing 查重；转发票没有。convertQuotation() 的 target === 'invoices' 分支直接 store.save。 缺失 重复点一次就多一张发票，金额重复计入应收。是否算 bug 取决于业务规则，见 §5 问题 4。
顺带纠正交接文档的一处数字

文档写「data.db 里还有 30 张旧表」。实际是 22 张（另 9 张是本期新建的系统表，再加 sqlite_sequence，共 32 张）。 数量不重要，重要的是下一节 —— 这 22 张表不是空的。

1.1 那 22 张「一行都没读写」的旧表，装着完整的第二份数据

交接文档说「应用程式一行都没读写（已全域搜过 FROM customers 之类语句，零命中）」。代码层面这句话成立。 但数据层面，这些表里是原系统全量数据的归一化副本：

为什么这是个架构隐患，而不是"以后清理一下"

任何未来的读者 —— 包括下一个 agent、做报表的人、接 BI 的人 —— 只要写一句 SELECT * FROM customers， 拿到的就是冻结在 2026-10-24 的旧数据，而且它看起来完全正常。这份副本没有任何标记说明它是弃用的。 这比"多占 20MB"严重得多：它是一份会骗人的数据源。

二选一，别放着：要么接上（把关系表变成主存储，见 §5 问题 1），要么明确封存（改名 _legacy_* 或导出成归档文件后 DROP）。

1.2 更正：这 22 张表不是「已经归一化好的数据」

我在第 1 轮口头说过「选 B 的话迁移成本比想象低很多，数据已经是归一化好的」。这句话不准确，在这里更正。

逐表核对字段后，这 22 张表是一次性的投影（改了名、丢了大半字段），不是可直接接管的主存储。原判断低估了 B 的工作量约一周。

但这三件事确实是便宜的，它们让 B 仍然明显优于 C：

  1. 主键完全对齐 —— schedule_employees.schedule_id 488/488 命中 records.id，迁移可以逐行 join 对账，不需要模糊匹配。
  2. 行数可作迁移校验 —— customers 1,608 / quotations 1,826 / schedules 13,113，抽完直接比对，差值必须是 0。
  3. 三张明细/关联表已经是对的 —— 报价明细、发票明细、排班人员，这三张直接接管，不用重建。
另一个核对结论：schedule_employees 的覆盖率是 100%，不是 3.7%

13,115 条排班里只有 488 条有 assigned_employees，看起来像丢了 96%。但我回去翻了原始导出 Schedule.json：原始 13,113 笔里也只有 488 笔的 assigned_employees 非空。 所以导入是忠实的，没有数据丢失 —— 是原系统本身就有 96% 的排班没指派人员（历史数据或走的是别的指派入口）。

这个事实的实践含义：「前线只看自己的班」这条权限规则，只对这 488 条生效。剩下 12,627 条对任何人都是"无主"的。 真正需要这条规则的是今后新建的排班，所以接 schedule_employees 的工作量很小，价值却集中在新增数据上。

2.2 P0 · 字段级屏蔽只挡住了列表，点「编辑」就现原形

证据 —— 同一个 office 账号，同一个报价单

根因：屏蔽逻辑写在 ui.mjs 的 renderValue()（第 880 行），而表单控件走的是 fieldInput()（第 995 行）， 后者完全不看 ctx.canSeeAmounts，直接把 esc(value ?? '') 填进 value=""。 所以"看不到金额"只在列表和详情成立，编辑页一律明文。

修法：fieldInput() 遇到 canSeeAmounts === false 且字段是金额类时，输出 value="" + placeholder="•••••" + 一个 hidden 保留原值（避免保存时把金额清空）。 更彻底的做法是 §4 阶段 1 的序列化层。

三 · 架构层问题（不是 bug，是分层缺失）

3.1 权限判据有三套，且默认放行

判据位置语义默认值
角色viewRoles/editRoles这个角色能不能进这一类实体拒绝
页面白名单accessible_pages这个账号能不能看这个页面放行 空值=不限制
记录级ownsRecord()这条记录是不是我的（按姓名比）放行 非 front 一律 true

三套判据分散在 core.mjs、server.mjs 两个文件、十几个调用点。任何新增路由只要漏写一句 assertEntity，就是 §2.1 那种缺口 —— 而 §2.1 已经真实发生了一次。这不是执行疏忽，是结构没有收敛点。

另外 ownsRecord() 用姓名比对：

const name = str(user.name).replace(/（[^）]*）/g, '').trim();
if (cfg.key === 'schedules') return arrEmployees(row.assigned_employees).some(n => n === name || n.includes(name));

n.includes(name) 是子串匹配 —— 员工「陳大文」会命中「陳大文（夜班）」，也可能命中任何包含这三个字的组合。 排班 13,116 条、员工来自历史排班反推（9 个姓名），这个匹配精度不足以承载"只看自己的"这条硬规则。

3.2 列表查询：每页读两次全表，且在单线程上同步执行

实测（隔离库） 
Quotation  1,796 笔 / 3.2 MB JSON   单次全量载入 27 ms
Schedule  13,115 笔 / 8.5 MB JSON   单次载入 + JSON.parse 116 ms

页面响应：/quotations 211 ms   /schedules 277 ms   /inventory 177 ms

根因：core.mjs:188-189

const source = store.list(cfg.key, …).filter(r => !r._draft);   // 第 1 次全量
const rows   = filteredRows(store, cfg, url, user);              // 第 2 次全量（内部又 store.list）

拿到全部行之后，搜索、筛选、排序全在 JS 里做，排序还用 localeCompare(…, 'zh-Hant') —— 13,115 行意味着上万次 ICU 排序调用。 最后才 slice((page-1)*50, …) 取 50 条。为了 50 行，读了 13,115 行。

单线程 Node + 同步 node:sqlite，这 277 ms 期间整个服务无法响应任何其他请求。 50 人规模下并发一上来就是串行排队。这不是"以后优化"，是上线即会遇到的第一个投诉。

另外两处无分页

应收台账与总账一次渲染全部：实测 /receivables 381 行 / 147 KB，/generalledger 524 行 / 230 KB。 页面本身 50 ms 就返回了，但 230 KB 的 HTML 在手机上渲染会明显卡。交接文档已把它列为 P0，确认属实。

3.3 单表 JSON：没有外键，也没有唯一约束

records(entity, id, data JSON, deleted) 这张表设计得很省事，代价是数据库无法保护任何业务不变量：

  • 没有外键 —— 删客户不会管单据；mergeCustomers 只能写脚本手工扫全表（38 实体 × 34k 行，在一个事务里跑）。
  • 没有唯一约束 —— 单号靠 nextNumber() 扫全表取 max+1，并发下会重号。报价 1,826 笔，扫一次全表。
  • 没有类型 —— 金额存成字符串还是数字取决于谁写的。num() 到处兜底，掩盖了脏数据。
  • 没有字段级并发控制 —— store.save() 是 {...previous, ...data} 整条覆盖，乐观锁靠 updated_date 字符串相等。

这套模型在 3 万条、10 人用时完全够。问题不在现在，在它无法平滑长大 —— 见 §5 问题 1。

3.4 运行期基础设施缺三样

缺什么现状后果
定时任务server.mjs 里没有任何 setInterval / cron。定期排程只能靠人在详情页点「立即产生到期排班」。「定期服务」这个功能的名字和实际行为不一致。一旦没人点，排班就不生成，前线当天看不到工单。
会话持久化const sessions = new Map()，存内存；Cookie 只有 HttpOnly; SameSite=Lax，无 Secure。每次重启全员掉线。多进程/多实例无法工作。上 HTTPS 后 Cookie 仍可能走明文。
工程化基线无 package.json / engines / .nvmrc / Dockerfile / 迁移版本表。migrate() 靠 CREATE IF NOT EXISTS + ensureColumn。换台机器 Node 版本不对就起不来（node:sqlite 是 Node 22 实验特性）。没有 schema 版本号，将来改结构无法回溯"这个库是第几版"。
一个必须先拆的地雷：演示登录默认是开的

migrate() 写入 demo_mode = '1'，/demo?as=management 直接发一个 management 会话。 我在隔离库上没有输入任何密码就拿到了 front 和 office 的会话（HTTP 302 + 有效 Cookie），management 走同一个 ids 映射分支。

目前靠 settings.demo_mode='0' 或环境变量 CPC_DEMO=0 关闭 —— 也就是说， “是否对局域网开放完全管理权限”取决于一个默认值为「开」的配置项。部署当天忘了改，就是后门。 建议：默认改成 '0'；启动时若检测到 '1'，在终端打一条显眼红字警告。

六 · 部署安全基线：代理后的真实 IP 与锁定策略

这是 Q3 = B（香港云 + HTTPS + nginx 反代） 引出的必答题。现状两个 bug 互为镜像 —— 根因是没有「谁是我的对端」这个单一事实来源，两个调用点各自猜。

调用点现在取的 IP代理之后的结果
audit() 写审计x-forwarded-for 第一段可伪造。攻击者自带 X-Forwarded-For: 8.8.8.8，审计里就永远是 8.8.8.8
recordLoginFailure()socket.remoteAddress恒为 127.0.0.1。锁定键 ip|email 退化成 127.0.0.1|email
第 2 行意味着什么：一个针对性 DoS

所有用户共享同一个"IP"。攻击者只要连续输错某人邮箱 5 次，锁定键就被写死，受害者本人从任何设备都登不进去， 而且攻击者可以轮着锁所有人。反过来，攻击者自己换台机器（或直接打 localhost）就能绕过自己的锁定。

6.1 第一步：Node 只跟 nginx 说话

// server.mjs 末尾
server.listen(PORT, '127.0.0.1');   // 不是默认的 0.0.0.0

绑定回环，公网只暴露 443。这样 socket.remoteAddress 恒为 127.0.0.1 —— 听起来正是问题所在， 但它同时确立了一个前提：「对端是 127.0.0.1」本身就等于「这个请求经过了 nginx」，于是 XFF 可信。信任判断从此有了依据。

6.2 第二步：一个函数，两个调用点

// lib/net.mjs
const TRUST = new Set(['127.0.0.1', '::1']);
const norm = (v) => String(v || '').trim().replace(/^::ffff:/, '');

export function clientIp(req) {
  const peer = norm(req.socket.remoteAddress);
  // 对端不是本机 → 说明有人直连 Node（配置错了），此时只能信 socket
  if (!TRUST.has(peer)) return peer;
  const chain = String(req.headers['x-forwarded-for'] || '')
    .split(',').map(norm).filter((v) => v && /^[0-9a-fA-F:.]{3,45}$/.test(v));
  // 关键：从右往左，第一个「不可信」的地址才是真实客户端
  for (let i = chain.length - 1; i >= 0; i--) {
    if (!TRUST.has(chain[i])) return chain[i];
  }
  return chain[0] || peer;
}
为什么必须从右往左 —— 这是全篇最容易做错的一处

nginx 的 $proxy_add_x_forwarded_for 语义是「把对端 IP 追加到请求头里已有的字符串后面」。 攻击者发 X-Forwarded-For: 1.2.3.4，nginx 转给 Node 的是 1.2.3.4, <真实IP>。

最左边那一段是攻击者自己写的，取它 = 审计里记了个假 IP（现状的 bug）。 取「最右的非可信地址」才是真实 IP。任何"取第一段"的实现都是错的，包括很多教程。

6.3 第三步：锁定改成两级计数，废掉 ip|email 联合键

单键锁定无法同时满足两件事：只锁 IP 会被换 IP 绕过；只锁账号会被恶意锁死别人。拆成两个独立计数器，各解决一半。 复用现有 login_failures 表，key 加前缀即可，不需要改表结构。

维度key阈值窗口挡住什么 / 不会挡住什么
账号acct:<email>8 次15 分钟挡针对某个账号的暴力破解；不影响其他任何账号 → 「锁一个人等于锁全部」消失
来源ip:<clientIp>40 次15 分钟挡撞库喷洒（一个 IP 试很多账号）；办公区 NAT 后多人共用出口，阈值要放大，故取 40

三条实现纪律：

  1. 登录成功只清 acct:，不清 ip:。否则攻击者注册/持有一个自己的账号，登录一次就把 IP 计数清零，喷洒限制形同虚设。
  2. 对外提示必须一致（统一「帳號或密碼錯誤」），不能让人从文案推断是哪一级触发 —— 否则等于告诉攻击者"这个账号存在且已被锁"。
  3. 账号锁定要可解除：/users 页给管理层一个「解锁」按钮（删 acct: 行）。15 分钟自动过期是兜底，不是唯一手段 —— 否则员工被锁只能干等。

6.4 第四步：HTTPS 下必须同步改的三件小事

项做法不改的后果
Cookie 属性改为 __Host-sid=…; Path=/; Secure; HttpOnly; SameSite=Lax（__Host- 前缀强制 Secure + 禁止 Domain，防子域覆盖）没有 Secure，浏览器可能在明文 HTTP 下也发送会话 Cookie
协议判断nginx 传 X-Forwarded-Proto；Node 仅在 https 时下发 Secure写死 Secure 会让本地 http://127.0.0.1:3000 调试直接登不进去
会话持久化把 sessions 从 new Map() 落一张 sessions 表（约 20 行）每次重启/发版全员掉线；云上每日重启一次 = 每天早上一片"登录失效"投诉
一条边界：IP 不是身份

即使 clientIp() 完全正确，IP 也只是网络层线索 —— NAT 后几十人共用一个出口，手机换基站就变。 蓝图要审计回答的是「谁看了哪个客户」，靠的是 actor_id；IP 只用于「异地登录」「同一账号多人共用」这类辅助判断。

所以优先级是 actor_id 正确 > action 正确 > IP 正确。现在前两项是对的，IP 这项修到"不可伪造"即可， 不必为它引入设备指纹之类的东西 —— 那是另一个量级的复杂度。

6.5 完整 nginx 片段（可直接用）

server {
  listen 443 ssl http2;
  server_name erp.example.hk;

  ssl_certificate     /etc/letsencrypt/live/erp.example.hk/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/erp.example.hk/privkey.pem;

  location / {
    proxy_pass http://127.0.0.1:3000;

    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

7.5 一个连带问题：发票根本没有折扣字段

转发票会丢掉表头折扣，导致发票金额高于报价

四种单据的 total_amount 公式各不相同（代码事实）：

Quotation      total = subtotal + freight - discount
Invoice        total = subtotal + freight        ← 没有 discount 字段
PurchaseOrder  total = subtotal + tax            ← 没有 freight
Bill           total = subtotal + tax            ← 没有 freight，且忽略明细折扣

convertQuotation() 转发票时复制了 freight_charges，但 discount 无处可放，直接丢弃。 结果：发票金额 = 报价金额 + 折扣额，等于多收客户一笔折扣钱。

目前 0 张报价用过表头折扣 / 运费 / 税，所以没有真实错账。但这是个埋着的雷： 一旦有人填了折扣，开票就多收，而且没人会发现（因为发票和报价单看起来都"正常"）。→ 这是第 3 轮问题 7。
