三 · A 组：测试全绿但功能是坏的（4 条）

A-1 前线的产品选择器被 P0 修复打断 回归 · 最高优先
现象
前线在「補給記錄」里新增物料，点产品输入框没有候选项（接口 403）
复现
curl -c f.jar "http://127.0.0.1:PORT/demo?as=front"
curl -b f.jar "http://127.0.0.1:PORT/api/pick?source=products"
  → 403
curl -b f.jar "http://127.0.0.1:PORT/new/supply_records"
  → 200，且页面 data-columns 内含 "source":"products"
根因
lib/pickers.mjs:255 的 PICK_SOURCE_EXTRA_ROLES 只给 employees 开了例外，漏了 products。products 实体页面对前线关闭，但补给表单确实需要它。
修法
products: ['front'] 加进 PICK_SOURCE_EXTRA_ROLES。**不要另写裁剪逻辑** —— pickFillForRole 已对非 accounting/management 剥掉 PICK_MONEY_FIELDS，放行选择器不等于放行成本价。
验收
① front → products 200，整份 JSON 搜不到 cost_price/supplier_price/unit_cost
② front 的补给表单能拉到产品
③ front → customers / contracts / purchase_orders 仍 403
④ accounting → products 仍有 cost_price
禁改
不要为了修这条，放松 customers / contracts / purchase_orders 的 strict 判定
A-2 办公室仍能从明细 JSON 读到每行小计 P1
现象
蓝图规定「办公室可见单价、不可见小计」，列表与详情已打码，但编辑页的明细数据原文里带着行小计
复现
office 打开 /edit/quotations/<id>，取 name="items" 的 textarea：
unit_price=900  total=900
unit_price=700  total=2100
根因
lib/ui.mjs:1029 的 items 分支直接 JSON.stringify(items)，未按 ctx.canSeeAmounts 裁剪
修法
canSeeAmounts === false 且 field.name === 'items' 时：每行**复制一份**再 delete total/subtotal/amount，然后序列化；itemCols 同步过滤这三列，避免前端渲染空列。必须复制后删，不能原地改（items 可能来自缓存）。
边界
只对 quotations / invoices / purchase_orders / bills 的 items 生效。stock_counts 明细含 difference（公式不同）**禁动**；receipts 的 items[].subtotal 是实收额（实测 11,050），**禁动**，剥掉就是真丢数据。
验收
① office 编辑页 items JSON 无 total 键，unit_price 仍在
② 原样提交后 total_amount 与提交前逐字节相同（服务端 recalculate 会补回）
③ management 打开同页仍可见行小计
A-3 报价表头「折扣」是死字段 P2
依据
已查证：原系统 Quotation.discount 在 1,826 张里 0 张非空；原系统 Invoice 根本没有该字段；PDF 模板只渲染明细 Disc 列，不渲染表头折扣；公司确认无折扣业务
位置
lib/config.mjs:225：field('discount', '折扣', 'money', { section: '報價摘要' })
修法
删掉这一项。**保留** moneyItemColumns 里的 { name:'discount', ... }（PDF Disc 列需要）；**不要动** AMOUNT_FIELDS 里的 'discount'
验收
① 报价表单无表头 name="discount"
② 明细 Disc 列仍在
③ 报价 PDF 与改动前逐字节相同
A-4 自动生成的库存调整单没有编号（= STK-09） P2
根因
lib/actions.mjs:50：defaultNumber() 开头 if (!Object.hasOwn(data, field)) return;，而三处 adjustment 对象字面量没有 adjustment_number 键 → 永远跳过编号生成
位置
actions.mjs:303（送貨出庫）、:359（沖銷／重過賬）、:410（盤點過賬）
修法
三处各补 adjustment_number: ''
禁改
**不要改 defaultNumber 本身**（牵连 8 个实体）；**不要回填历史空白编号** —— 实测生产库 9,566 张调整单里，带 source_delivery_id/source_stock_count_id 的自动单 0 条，没有可回填的对象
验收
① 盘点过账生成的调整单编号形如 ADJ-2026-#####
② 送货过账同样
③ 两张编号不重复
④ run-tests 的 STK-09 由 FAIL 转 PASS

四 · B 组：既有缺陷（6 条）

编号等级根因（已核准）修法验收判据
PERM-06S2 菜单与实体的角色来源不一致：config.mjs:128 NAV 给「盤點記錄」用 BACK_OFFICE（含 accounting），而 :498 的 viewRoles 是 OFFICE_ADMIN（不含）→ 会计看得见菜单，点进去 403 两处角色来源合一：NAV 改读 ENTITIES[key].viewRoles；顺带给其他菜单项做一次一致性核对 accounting 侧栏不再出现「盤點記錄」，或点进去 200 —— 两者取其一，但不能是「可见且 403」

SCH-07S3 手动排班的 total_hours 不计算；只有定期排程生成时按 estimated_hours 汇总 saveSchedule 内按 start_time/end_time 差值汇总；跨日另计 09:00–11:00 + 13:00–14:30 的排班，total_hours = 3.5
DAT-02S2 历史汇入的 22 张报价只有表头金额、明细单价/小计为 0；recalculate 以明细重算，打开再保存会把金额归零 先出这 22 张的清单（含单号与当前金额）；recalculate 在「明细合计为 0 且表头有值」时保留表头，或加显式标志位。修好之前禁止直接编辑这 22 张 22 张逐张「打开→保存」，total_amount 不变；新单据的正常重算不受影响
DAT-02 有数据安全前置条件

在修好之前，任何人编辑这 22 张报价都会把金额清零，而且没有任何提示。建议立刻做两件事：① 出清单贴到群里，让办公室别碰； ② 修法上线前，对这 22 张做一次只读备份快照。
