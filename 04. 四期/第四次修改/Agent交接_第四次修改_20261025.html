030 秒摘要

如果你只讀一段

  1. 這是一個零依賴的 Node 22 應用：node:http 手寫路由 + node:sqlite。沒有框架、沒有 build、沒有 node_modules。
  2. 全部業務資料存在 data.db 的一張 records 表裡（entity + id + data(JSON)），欄位定義在 lib/config.mjs 的 ENTITIES。
  3. 起服務就是 node server.mjs，開 http://127.0.0.1:3000，用 /demo?as=front 之類的連結免密登入。
  4. 這一輪（第四次）只動了 UI 與 4 個真實缺陷：沒有改 DB schema、沒有加依賴、沒有動路由與權限模型。
  5. 改完 lib/*.mjs 或 server.mjs 一定要重啟，沒有熱重載。
三件會直接弄壞系統的事
  1. 改 .navgrp>summary 的字重——verify-operation-2.mjs 用字面 CSS 斷言 font-size:13px;font-weight:700，改了 55 項驗收直接紅。
  2. 給「新增」彈窗填 __id——後端會當成編輯一筆不存在的記錄，回 404，而且錯誤訊息會被二次 404 吞掉（這就是第 5.2 節的原始 bug）。
  3. 在瀏覽器端呼叫 isIntegerField()——它是 Node 端函式，ReferenceError 會讓整個明細編輯器初始化失敗，「新增一行」完全沒反應。

1.4 權限其實有兩層

  • 角色：assertRole(user, roles, pageKey)，roles 寫在 NAV 與每個實體的 viewRoles/editRoles。
  • 頁面白名單：assertAccessible(user, pageKey)，讀 users.accessible_pages（JSON 陣列或逗號字串）。留空＝不限制。這裡有一張 PAGE_ALIASES 表，把新舊頁面名對到同一組 key，改頁名時要一起改。
  • 記錄級：ownsRecord() 只對 front 生效。規則容易記錯，直接列出來：
    • schedules：只能看/改「指派給自己」的。
    • work_records：全部可看，不可編輯。
    • supply_records：全部可看，只能改自己的（employee_name 或 created_by 相符）。
    • leave_records / check_ins / attendances：只能看自己的。

3資料模型

只有一張業務表。所有實體共用它，靠 entity 區分：

CREATE TABLE records (
  entity       TEXT NOT NULL,      -- 'Quotation' / 'Customer' / 'SupplyRecord' …
  id           TEXT NOT NULL,
  data         TEXT NOT NULL,      -- 整筆記錄的 JSON
  deleted      INTEGER DEFAULT 0,  -- 軟刪除，回收桶靠它
  created_date TEXT,
  updated_date TEXT,
  PRIMARY KEY (entity, id)
);
項目現況
實體數38 個（定義在 ENTITIES）
記錄總數34,053 筆，其中 46 筆在回收桶
最大三個Schedule 13,116 · StockAdjustment 9,566 · Notification 5,103
其他系統表users / settings / quota / audit_log / notifications / holidays / login_failures / signatures
刪除策略軟刪除 deleted=1；回收桶每日還原／清除上限 10 次（TRASH_DAILY_LIMIT）
資料庫裡那 30 張舊表不要碰 data.db 裡還有 customers、quotations、invoices… 等 30 張表，那是原系統結構的殘留，應用程式一行都沒讀寫（已全域搜過 FROM customers 之類的語句，零命中）。真正在跑的是 records。要清理舊表是獨立的一件事，先備份再動，別在功能開發中順手做。

資料從哪來：seed.mjs 讀 CPC_DATA_DIR 下的 <Entity>.json，INSERT OR IGNORE 進 records。它不會覆蓋既有業務修改，也可以只補單一實體：node seed.mjs Customer Quotation。

POST /save/contracts
  └─ bodyWithCsrf(req, session)                 // CSRF 不符 → 403

            ├─ id = cleanId(fields.__id)
            ├─ existing = id ? store.get(cfg.key,id) : null
            ├─ 防禦回退：id 有值但查不到、且沒有 __expected_updated → 當新增

            │    ├─ for field of cfg.fields → required 檢查

            ├─ 樂觀鎖：__expected_updated ≠ existing.updated_date → 409「已被其他人更新」
            └─ store.save() → redirect(__back || cfg.listPath)
保存失敗時走的那條路，是上一輪 bug 的現場 錯誤發生後，server.mjs 的 catch 會呼叫 entityForm({id: body.fields.__id, error}) 想「把表單連同錯誤訊息重繪」。但 entityForm() 開頭也有一道「記錄必須存在」的檢查——如果 __id 是壞的，這裡會再拋一次 404，使用者最後看到的是沒有任何訊息的空白錯誤頁。現在的寫法是先確認記錄還在，不在就清空 __id 再重繪。

5.2 補給／請假存檔 404（真實缺陷，影響兩個功能）

症狀：/mysupply 按「新增記錄」→ 填完 → 按「建立記錄」→ 沒有任何提示，記錄也沒出現。

GET  /mysupply?new=1      → 200，彈窗內含
     <input type="hidden" name="__id" value="sup_mvnigg9s_661c25f30d8b">
POST /save/supply_records → 404（空白錯誤頁）

根因：recordDialog()（lib/core.mjs）預先生成一個新 ID 給 __new_id，同時也寫進了 __id。後端 saveEntity() 看到非空 __id 就當成「編輯既有記錄」，store.get() 找不到 → 404；catch 再呼叫 entityForm(壞 id) → 二次 404，連錯誤訊息都吞掉。

修法（三處）：

檔案改動作用
lib/core.mjshiddenInput('__id', '')新增彈窗只送 __new_id（根治）
lib/actions.mjs__id 查不到且無 __expected_updated → 當新增處理擋住同類寫法再次造成 404
server.mjs重繪前確認記錄還在，否則清空 __id錯誤訊息能顯示，使用者填的內容不丟
為什麼前三輪驗收沒抓到 verify-frontline.mjs 是直接對 /save/leave_records 發 POST，payload 自己寫 __id:''——正好繞過壞掉的那個欄位。它測的是「後端能不能存」，不是「畫面送出來的東西能不能存」。所以後來補了一支專門斷言「彈窗 __id 必須為空」的腳本。

5.3 數量一律整數

原本明細裡的數字輸入是全域 <input type="number" step="0.01">，數量、單價、金額共用一套，所以可以打 2.5 瓶。

層實作效果
前端type="text" inputmode="numeric" pattern="[0-9]*"，input 時把 2.5 截成 2手機彈數字鍵盤，打不進小數點/負號
後端assertIntegerQuantities() 掛在 prepareRecord()直送 2.5 → 400「第 1 行的『數量』必須為整數，不可有小數」
歷史資料編輯既有記錄且該值未改動時放行原系統匯入的 204.5 庫存仍可改名、改價、存檔
 
// lib/utils.mjs
export const INTEGER_FIELD_NAMES = /^(quantity|qty|stock_quantity|quantity_change)$/;
export const isIntegerField = (field) => field?.integer === true
  || (field?.integer !== false && INTEGER_FIELD_NAMES.test(String(field?.name || field?.key || '')));

刻意不納入 quantity_before / quantity_after / difference / actual_quantity——這些是「現有庫存 ± 變動」推出來的，起點本身可能是 204.5，硬性取整會讓數字對不上。

覆蓋：補給（產品/工具數量）、報價／帳單／送貨單明細、服務報告使用產品、產品庫存、庫存調整。未覆蓋：盤點單的 actual_quantity（4,853 項中有 40 筆歷史小數，見 §9）。

5.4 彈窗欄位調整（員工 ID）

補給與請假彈窗都有「員工 ID」，實際操作時沒人會看。改成 hidden: true——畫面上不渲染，但仍以隱藏 input 提交；formGrid() 會輸出 <input type="hidden">，員工選擇器的 pkApplyFill() 仍找得到 [name="employee_id"] 回填，所以「辦公室替某位員工登記」的關聯不會丟。

移除後 2 欄 grid 出現空格，順手重排：

  • 補給：日期 ｜ 補給位置 → 員工姓名（整列）
  • 請假：員工姓名 ｜ 類型 → 開始 ｜ 結束 → 請假天數 ｜ 狀態 → 原因（整列）→ 備註（整列）

5.5 下拉「一滑就關」

// 修好之前：一行就讓 50 筆的清單無法滾動
window.addEventListener('scroll', close, true);   // true = 捕獲階段

捕獲階段會在事件到達目標之前就觸發，所以「在清單裡面自己捲」也會被 window 收到 → 直接 close()。產品清單 50 筆、scrollHeight 1,694px、可視高度 418px，一滑就關。

// 修好之後：分三種情況
window.addEventListener('scroll', function (e) {
  if (menu.hidden) return;
  var t = e.target;
  if (t && t !== document && (t === menu || menu.contains(t))) return;   // ① 清單自己捲 → 不關
  if (!input.isConnected) { close(); return; }
  var r = input.getBoundingClientRect();
  if (r.bottom < 0 || r.top > window.innerHeight) { close(); return; }   // ③ 錨點離屏 → 關
  place();                                                              // ② 頁面/彈窗捲動 → 重定位
}, true);

順帶修好另一半：以前在彈窗裡往下捲找欄位，只要下拉開著也會被關掉；現在它會跟著輸入框移動。

7 server.mjs 保持 CRLF；lib/*.mjs 保持 LF diff 從幾十行爆成整檔重寫，review 失效 用 Node 數 \r\n 與 \n，不要用編輯器猜

#現象原因與解法

3複製 data.db 後，驗證環境少最新資料WAL 模式：資料還在 data.db-wal（當時 1.6 MB）。先 PRAGMA wal_checkpoint(TRUNCATE)，或一併複製 -wal／-shm。

9長名稱被截成「…」td.nw{max-width:210px;text-overflow:ellipsis}。需要完整顯示就在欄位定義加 nw:false，不要直接改全域 CSS。
