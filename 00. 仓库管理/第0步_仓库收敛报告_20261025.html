二、实测发现的四件事

1 · 「第四次修改」不是第三份代码，是同一份

你选的是「四期 · 第四次修改」，我逐个比对了 SHA256：程式快照_20261025/ 与 系统代码/ 的 11 个代码文件完全相同。但快照目录里没有 seed.mjs、schema.json、data.db 和启动脚本，单独拿去跑不起来。所以真正能作为生产副本的只有 系统代码/，快照从此改由 tag 承担。

2 · README 指的目录名不存在

README 写的是 04. 四期/系統代碼/（繁体「系統」），实际目录是 系统代码（简体）。这个错字会让任何按文档找代码的人（包括下一个 agent）在第一步就扑空。已修正。

纠正我自己上一轮的一个判断。我说过 README「lib 写 10 个却只列了 9 个」—— 这条是错的。重新核对后，README 列出的正是 10 个，包含 pickers.mjs。真正漂移的只有目录名的繁简。

3 · 缺陷清单其实已经有了

測試設計_20261025/缺陷清單.csv 已经存在，8 条，字段完整：等级、优先级、现象、实测、根因、修复建议、证据、状态。所以第 1 步不是「从零建缺陷库」，而是把架构师那 3 个 P0 合并进来，再补三个字段：owner、回归用例 ID、发现轮次。

4 · 换行符是下一个隐患

提交时出现大量 LF will be replaced by CRLF 警告。server.mjs 是 CRLF，lib/*.mjs 是 LF，工具脚本用 Python 写文件时还会再把 LF 翻成 CRLF —— 你的记忆里记过一次 diff 爆到 +702/−702。这次没动它（会牵出一整文件的重写），留作独立一次提交处理。

三、怎么回滚

这次整理是一个独立提交，回滚只需一步，且不会丢任何本地文件：

git revert b00f000          # 推荐：保留历史，重建被移除的跟踪
git reset --hard bb562c5    # 激进：回到整理前，但会丢掉新增的 00. 仓库管理/
本地磁盘上的 03. 三期/系统代码/、各轮 程式快照/ 本来就没被删除，不论怎么回滚都还在原处。
