# 角色卡索引

九个角色，覆盖一条完整开发链。前五个已经在跑，后四个是补上的缺环。

## 全景

```
                    ┌─ 规格官 ──────────┐
原系统 ─┬─ 数据下载 ─┤                   ├─ 架构师 ─ 开发 ─ 测试 ─┬─ 发布官 ─ 运维
        └─ 代码下载 ─┘                   │                        │
                    └─ 数据管家 ────────┘                        │
                                                                  │
                          QA 资产管家 ────────────────────────────┘
```

## 五个在跑的

| 角色 | 一句话 | 产出 |
|---|---|---|
| 原系统数据下载 | 把 40 张表、2,012 个附件完整取回 | `02. 数据导出/`、`03. 附件/`、完整性报告 |
| 原系统代码下载 | 把前端/后端反编译成可读源码 | `05. 源码分析/`、交互审计 |
| 架构师 | 判断「分层对不对」，复现 P0 | `架构审核_*/`、优化路线、三问 |
| 开发 | 按缺陷与用例改代码 | 代码提交、交接 HTML、SHA 清单 |
| 测试 | 设计用例、跑基线、出报告 | `測試設計_*/`、`測試結果_基線.json` |

## 四个补上的

| 角色 | 补的是哪个洞 | 起点文件 |
|---|---|---|
| [规格官](规格官.md) | 原系统会失效，而它才是裁判 | `05. 源码分析/frontend/beautified/app.js` |
| [数据管家](数据管家.md) | 数据「完整」但不「自洽」 | `data.db` + 原始导出 |
| [发布官](发布官.md) | 没有版本、没有回滚演练 | `defects.csv` + run-tests |
| [QA 资产管家](QA资产管家.md) | 修过的 bug 会回来，断言会写死实现 | `plan.mjs` + `run-tests.mjs` |

## 什么时候叫谁

| 情况 | 叫谁 |
|---|---|
| 「原系统到底是什么行为？」 | 规格官 |
| 「这单金额不对 / 重名怎么处理？」 | 数据管家 |
| 「这一版能不能交？」 | 发布官 |
| 「这 bug 修好了吗？会不会再犯？」 | QA 资产管家 |
| 「这么分层对不对？」 | 架构师 |
| 「改。现在改。」 | 开发 |

## 三个角色共同遵守的一条

**产出必须是文件，不是结论。**

- 规格官的结论 → `spec/*.md`（带证据）
- 数据管家的结论 → `例外_*.csv` + `處置表.csv`
- 发布官的结论 → tag + `CHANGELOG.md` + 回滚演练记录
- QA 的结论 → `defects.csv` 状态 + 通过记录

口头说的「我查过了」「应该没问题」，在下一个人那里等于零。

## 交接契约（最小集）

| 上游 → 下游 | 必须是 |
|---|---|
| 架构师 → QA | 缺陷写进 `defects.csv`，不能只写在 HTML 报告里 |
| QA → 开发 | 用例 id + 复现步骤，不能只给「有个 bug」 |
| 开发 → QA | 提交哈希 + 改了哪几个文件 |
| QA → 发布官 | P0 是否全绿 + 基线同比 |
| 发布官 → 所有人 | tag + CHANGELOG + 回滚方式 |
