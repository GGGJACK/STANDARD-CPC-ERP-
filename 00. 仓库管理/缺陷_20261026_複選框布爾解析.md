# 缺陷詳解：複選框（checkbox）勾選永遠存不進去

| 項 | 值 |
|---|---|
| 缺陷號 | `FRM-01`（`00. 仓库管理/defects.csv`） |
| 等級 / 優先級 | S2 / P1 |
| 發現 | 2026-10-26，部署驗收時由業務方實際發布公告觸發 |
| 影響版本 | `v4.5-20261025`（`ed9ec7c`）及之前所有版本 |
| 修復分支 | `feat/fix-checkbox-bool` |
| 回歸用例 | `ANN-01` ~ `ANN-04`（`測試設計_20261025/plan.mjs`，實作於 `系统代码/test.mjs`） |
| 狀態 | 已修待驗 |

---

## 1. 一句話結論

表單把複選框寫成「hidden `0` + checkbox `1`」兩個同名參數；`parseBody` 把同名參數存成**陣列** `['0','1']`；而 `bool()` 只做**精確比較** `value === '1'`。陣列永遠不等於字串，於是**勾不勾都是 `false`**。

---

## 2. 現象與復現

### 業務現象

發布公告時勾選「啟用」，保存成功（302），但公告欄仍然是空的。反覆編輯也一樣，沒有任何報錯。

### 最小復現（隔離副本，勿在正式庫操作）

## 3. 根因（代碼級）

### 資料流

```
HTML 表單
  <input type="hidden"   name="is_active" value="0">          ← 恆送出
  <input type="checkbox" name="is_active" value="1" checked>   ← 勾選才送
        ↓  application/x-www-form-urlencoded
  is_active=0&is_active=1
        ↓  parseBody()            lib/utils.mjs:161-167
  fields.is_active = ['0','1']     ← 同名參數被 concat 成陣列
        ↓  saveEntity()           lib/actions.mjs:242
  data[field.name] = bool(value)
        ↓  bool()                 lib/utils.mjs:27（修復前）
  value === '1'  →  false         ← 陣列 !== 字串
```

### 關鍵三段代碼

`lib/utils.mjs:161`（修復前）

```js
const params = new URLSearchParams(raw.toString('utf8'));
const fields = {};
for (const [key, value] of params) {
  if (fields[key] !== undefined) fields[key] = [].concat(fields[key], value);  // ← 變陣列
  else fields[key] = value;
}
```

`lib/actions.mjs:242`

```js
else if (field.type === 'checkbox') data[field.name] = bool(value);
```

`lib/utils.mjs:27`（修復前）

```js
export const bool = (value) => value === true || value === 1 || value === '1' || ...;
```

### 為什麼「不勾」反而能正確表達

不勾選時只送出 `is_active=0`，是**單值**字串，`bool('0') === false` 正確。
只有「勾選」這條路徑會產生陣列——所以現象是**只能關、不能開**，隱蔽性極高。

### 第二處同源缺陷

`server.mjs:700,702`（修復前）直接比較：

```js
active: fields.active === '1'
```

`fields.active` 是 `['0','1']` 時同樣恆 `false`，導致**用戶永遠無法被啟用**；且第 700 行的自我保護判斷會誤觸，保存自己的管理帳號會被 409 擋下。

## 4. 影響面

| 模組 | 欄位 | 後果 |
|---|---|---|
| 公告 Announcement | `is_active` | 發布後公告欄不顯示，靜默丟失 |
| 地址 Address | `is_active` | 新地址無法啟用 |
| 郵件模板 EmailTemplate | `is_active` | 模板無法啟用 |
| 會計科目 Account | `is_active` | 科目無法啟用 |
| 用戶管理 User | `active` / `must_change` | 帳號無法啟用；首次改密勾不上 |

凡是 `schema.json` 裡 `type: "boolean"` 且以 `checkbox` 渲染的欄位，**全部失效**。

---

## 5. 為什麼三層都沒抓到

1. **設計層**：`plan.mjs` 原本**沒有公告模組**，公告只在權限矩陣裡出現（「公告頁全員可直讀」），沒有「發布→顯示」的用例。
2. **自動化層**：`test.mjs` 從未 import 過 `Announcement`（`grep -c Announcement test.mjs` = 0）。而且 `test.mjs` 的 `post()` 用 `new URLSearchParams(payload)`，陣列會被序列化成 `"0,1"` 這種**單值**，**結構上不可能重現本缺陷**。
3. **驗收層**：部署時只驗了「頁面 HTTP 200」「列表筆數正確」，屬於**只驗讀、不驗寫**。這類「寫進去了但值不對」的缺陷天然漏網。

> 附帶問題：`test.mjs` 靠 `/demo?as=` 免密登入，而 `demo_mode` 預設關閉（見 commit `3b56cc7`），測試在此配置下**連第一步取 CSRF 都過不去**。跑之前需在測試庫 `insert into settings(key,value) values('demo_mode','1')`。

## 6. 修復內容

### `lib/utils.mjs`

```js
// 表單裡的 checkbox 會同時送出 hidden 的 "0" 與勾選時的 "1"。parseBody 遇到同名欄位會存成陣列，
// 取最後一個值才符合「後送覆蓋前送」的表單語義，否則 bool(['0','1']) 恆為 false，勾選永遠無法生效。
export const bool = (value) => {
  const v = Array.isArray(value) ? value[value.length - 1] : value;
  return v === true || v === 1 || v === '1' || v === 'true' || v === 'on' || v === 'yes';
};
```

取**末值**而不是首值，是刻意的：HTML 表單同名參數的語義就是後送覆蓋前送，隱藏欄位永遠在前，勾選值在後。

### `server.mjs:700,702`

```diff
- if (fields.id === user.id && (fields.role !== 'management' || fields.active !== '1'))
+ if (fields.id === user.id && (fields.role !== 'management' || !bool(fields.active)))
- active: fields.active === '1'
+ active: bool(fields.active)
```

### `test.mjs`（讓測試能重現瀏覽器行為）

```js
// 值為陣列時逐個 append，模擬瀏覽器送出同名參數
const params = new URLSearchParams();
for (const [key, value] of Object.entries(payload)) {
  if (Array.isArray(value)) for (const item of value) params.append(key, String(item));
  else params.append(key, String(value ?? ''));
}
```

## 8. 給後續接手者的注意事項

1. **不要改 `parseBody` 為「後送覆蓋前送」了事**。它是通用解析器，其他欄位可能依賴陣列（多選、多檔案）。修在 `bool()` 這層影響面最小。
2. **`bool()` 的陣列分支不能刪**。它同時保護 `checkbox`、`select multiple`、以及任何重複提交的表單。若日後新增布爾欄位，走 `field(..., 'checkbox')` 即自動受益。
3. **`test.mjs` 的 `post()` 必須保留陣列支援**，否則 `ANN-01` 會退回「送單值」而失去回歸意義——這正是本缺陷當年逃過測試的原因。
4. **判斷「修完了」的標準**：`ANN-01~04` 全綠 + `defects.csv` 該行狀態改 `已關閉`。口頭「修好了」不算。
5. **同類風險排查**：搜 `=== '1'`、`=== "true"`、`!== '0'` 這類對表單值做精確比較的寫法，都應改用 `bool()`。目前全庫已無殘留。
6. 本缺陷已寫入 `defects.csv`，`回歸用例` 欄指向 `ANN-01`，符合 §8「沒有回歸用例的修復不算修完」。
