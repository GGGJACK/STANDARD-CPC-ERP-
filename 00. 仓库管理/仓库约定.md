## 1. 单一生产副本

| 事项 | 结论 |
|---|---|
| 唯一生产代码 | `04. 四期/系统代码/` |
| 判定依据 | 唯一同时具备 `seed.mjs` + `schema.json` + `data.db` + 启动脚本、可独立运行的副本 |
| 校验方式 | 与 `04. 四期/四次修改/程式快照_20261025/` 的 11 个代码文件 SHA256 逐一相同（见 `BASELINE_SHA256_20261025.csv`） |

`01. 一期` ~ `03. 三期` 以及各轮「程式快照」都是历史切片，**只读，不再修改**。它们的代码文件已移出版本控制，本地文件仍在原目录，不会被删除。

## 3. 什么进仓库，什么不进

**进**：`.mjs` `.json`（非数据） `.html`（交付文档） `.md` `.csv`（清单） `.bat`

**不进**：

| 内容 | 原因 |
|---|---|
| `data.db` `*.db-wal` `*.db-shm` | 54MB 且含 1,608 条真实客户资料 |
| 各轮「程式快照_*」 | 与生产副本重复，是"代码会乱"的主因 |
| `01.~/02.~/03. 系统代码/` | 历史切片，本地留档即可 |
| `04. 四期/系统代码/uploads/` | 运行时上传产物 |
| `backup-*/` `_歷史版本/` | 本地回滚用 |
| 附件（943MB）、`05. 源码分析/frontend/`（37MB） | 走项目资产库 |

完整规则见 `.gitignore`。

## 5. 提交前门槛

**进 `dev`**：`node --check` 通过即可。

**进 `main`（M0 放行）**：五道全过，缺一不进。

- [ ] `node --check` 全过（`04. 四期/系统代码` 下 `server.mjs` + `lib/*.mjs`）
- [ ] `run-tests.mjs` **P0 分组 100%**（S2/S3 可排期，但不得比上一版多）
- [ ] `test.mjs` 业务验收 **422/422**（隔离副本，端口 3100）
- [ ] `compare-ui.mjs` DOM 对照 **34/34**（需 Edge 开 9222）
- [ ] `rollback-drill.mjs` 回滚演练 **全过**（从 tag 恢复代码能跑）
- [ ] 没有 `data.db`、`backup-*`、`uploads/` 被 `git add`

> 用例数随覆盖增加而变，以最近一次记录的基线为准：`test.mjs` 原 **413**，2026-10-26 新增公告模组 ANN-01~04（10 条断言）后为 **422**；`run-tests.mjs` 118 项、P0 61、历史基线 112 通过（6 条为 `defects.csv` 里待修的 P1/P2）。

四条命令：

```bash
# 可执行验收（自带隔离副本，端口 3102；--src/--db 默认指向本仓库与程式目录下的 data.db）
node "04. 四期/測試設計_20261025/run-tests.mjs" --db "D:/CPC-ERP/_runtime/data.db"

# 业务验收（先起隔离服务：PORT=3100 DB_PATH=<副本>）
TEST_BASE=http://127.0.0.1:3100 DB_PATH=<副本> node "04. 四期/系统代码/test.mjs"

# DOM 对照（先起无头 Edge：--remote-debugging-port=9222 --user-data-dir=<独立目录>）
node "04. 四期/工具/compare-ui.mjs"

# 回滚演练（自动导出 tag、起服务、冒烟 12 条、清理）
CPC_DB="D:/CPC-ERP/_runtime/data.db" node "04. 四期/工具/rollback-drill.mjs" <tag> 3105
```

**脚本可移植性**（2026-10-26 修复，缺陷 `TST-02`）：仓库根由脚本自身位置推导，不再写死作者本机路径；可用 `CPC_ROOT` / `CPC_DB` / `CPC_OUT` 覆盖，`run-tests.mjs` 另有 `--src` / `--db`。三套脚本都会在**各自的隔离副本**内写入 `demo_mode=1`（验收靠 `/demo?as=` 登入），**来源库不受影响**，不需要为了跑测试去改正式库设置。

> **不要为了全绿而删断言**。改不动就先 tag 一个 `wip-` 前缀。
> 断言与实现长期不一致时（如别名路由 200 vs 302），改断言要在提交里单独说明理由，且**只能改成验行为，不能改成放水**。

## 7. 提交信息格式

沿用现有风格，前缀 + 中文描述：

```
feat: 报价单支持批量导出
fix: 补货/请假弹窗 __id 非空导致 404
chore(repo): 收敛为单一生产副本
docs(readme): 修正生产目录名
test: 补 3 个 P0 断言（越权/掩码/重名）
```

一句话说清"改了什么"，不写"更新文件"这类无信息量的描述。

## 8. 缺陷库

`00. 仓库管理/defects.csv` 是**唯一缺陷来源**，架构师、开发、测试三方都读它、都改它。

| 字段 | 规则 |
|---|---|
| `id` | 模块前缀 + 序号（`STK-06`、`SEC-01`）。**永不复用、永不删除**，作废改状态 |
| `等級` | S1 数据损坏/泄漏 · S2 主流程受阻 · S3 体验或一致性 |
| `優先級` | P0 阻断上线 · P1 本轮修 · P2 排期 |
| `owner` | `agent(dev)` / `agent(test)` / `待指派`。谁认领谁改 |
| `回歸用例` | 对应 `plan.mjs` 里的用例 ID。**没有回归用例的修复不算修完** |
| `發現於` | 哪个 agent、哪一轮发现的（用于回溯"为什么之前没抓到"） |
| `狀態` | `待修` → `修復中` → `待回歸` → `已修待驗` → `已關閉`；不接受"修好了"这种口头状态 |
| `修復於` | 填提交短哈希，没提交就是空 |

两条纪律：

1. **修一条、跑一条、改一行状态**。不要攒着一起改，否则回归对不上。
2. **不许为了全绿而把缺陷改成需求**。判不了就升级给业务确认，先标 `待確認為需求`。

数据来源：`04. 四期/測試設計_20261025/` 的 8 条与 `04. 四期/架构审核_20261025/` 的 3 条 P0 已合并进本表。

**派生文件不是本表**：跑 `build-plan.mjs` 会生成 `測試設計_20261025/缺陷清單_測試派生.csv`，它只反映「本次基线里失败的那几条」，是自动产物。要查负责人、回归用例、修复版本，看 `defects.csv`。

**需要完整根因时**：`defects.csv` 一格写不下代码级分析。凡涉及多模块、或容易被后来的 agent 改回去的缺陷，另写一篇 `00. 仓库管理/缺陷_<日期>_<主题>.md`，在 `證據` 栏指向它。目前有：

| 缺陷 | 详解文档 |
|---|---|
| `FRM-01` 複選框勾選存不進去 | `缺陷_20261026_複選框布爾解析.md` |
