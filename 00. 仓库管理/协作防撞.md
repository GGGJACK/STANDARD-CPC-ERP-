# 协作防撞

> 这份文件只解决一个问题：多个 agent 同时动这个仓库时，怎么不互相覆盖。
> 先看已经发生过的一次真实撞车，再给规则。

---

## 一、复盘：21:28–21:44 那次撞车

四个 agent 在同一小时里干活：

| 谁 | 分支 | 动了哪些文件 | 结果 |
|---|---|---|---|
| A | `feat/perm-hardening` | `server.mjs`、`lib/pickers.mjs`、`lib/store.mjs` | 与 B、C 零冲突 |
| B | `feat/field-masking` | `lib/ui.mjs`、`lib/config.mjs` | 与 A、C 零冲突 |
| C | `feat/data-integrity` | `lib/actions.mjs` | 与 A、B 零冲突 |
| D（本会话） | `dev` | `server.mjs`、`pickers.mjs`、`ui.mjs`、`actions.mjs` | **和 A、B、C 全部冲突** |

三个 feat 分支之间一次冲突都没有 —— 因为它们按**文件域**切开了，各占一块。
冲突全部来自 D：一个人把四个域全占了。

**结论：撞车不是因为「并行」，是因为「没有申报领地」。**

同一个缺陷被修了三遍（`/api/pick` 两次、金额掩码两次、盘点冲销两次），
最后必须人工判断「谁的实现留」，这比串行做慢得多。

## 二、三条铁律

### 铁律 1：一个 agent = 一个 worktree + 一个分支 + 一个端口 + 一份 DB 副本

四样必须一一对应，任何一样共用就会出事：

| 资源 | 共用会怎样 |
|---|---|
| worktree | 两个人轮流改同一个工作区，`git status` 分不清谁改的 |
| 分支 | 提交交错，rebase 时全是对方的 commit |
| 端口 | `EADDRINUSE`，或者更糟：测到的是对方的服务 |
| `data.db` | 一方过账、一方删单，账目对不上，且分不清是谁写的 |

### 铁律 2：改代码前先 claim，claim 是排他的

不 claim 就等于声明「我不在乎被覆盖」。
`claim` 会检查域冲突、端口冲突、分支冲突，任一冲突就拒绝。

### 铁律 3：真相文件单写者

`defects.csv`、`plan.mjs`、`run-tests.mjs`、`仓库约定.md`、`协作防撞.md`
只允许 **QA 资产管家** 写。其他 agent 要改，只能提「建议」或写进自己的租约备注，等 QA 落。

理由：这几份文件一旦被并行改，冲突一定发生在语义层（同一个用例 id、同一条缺陷状态），
合并时 git 帮不上忙。

## 三、文件域（claim 的单位）

| 域 | 覆盖文件 | 谁常占 |
|---|---|---|
| `API` | `server.mjs`、`lib/pickers.mjs` | 路由、权限、选择器 |
| `VIEW` | `lib/ui.mjs`、`lib/core.mjs` | 表单、表格、渲染 |
| `BIZ` | `lib/actions.mjs` | 业务动作、事务 |
| `DATA` | `lib/store.mjs`、`lib/documents.mjs` | 存储、单据、打印 |
| `CONFIG` | `lib/config.mjs` | **热点，必须独占** |
| `TEST` | `plan.mjs`、`run-tests.mjs`、`defects.csv` | 只给 QA |

### 为什么 `config.mjs` 单独一个域

它是唯一「所有人都会碰」的文件：加字段、改字段、调 NAV、调权限都在这。
两个 agent 同时改它，冲突概率接近 100%，而且冲突点在 JSON 结构里，很难肉眼合。

所以：**改 `config.mjs` 必须独占 `CONFIG` 域，且尽量把改动压缩到一次提交**。

一个任务跨域是常态（比如「会计菜单死链」要改 `config.mjs` 的 NAV + `core.mjs` 的渲染）。
跨域就 claim 多个域，工具会检查每一个是否空闲。

## 四、开工前 30 秒

```bash
node "00. 仓库管理/租约.mjs" status
```

输出会告诉你：谁在干什么、占了哪些域、用的哪个端口、有没有过期没释放的租约。

确认空闲后：

```bash
node "00. 仓库管理/租约.mjs" claim \
  --agent dev1 \
  --task "PERM-06 会计菜单死链" \
  --domains CONFIG,VIEW \
  --port 3110 \
  --branch feat/perm-06 \
  --worktree "F:/_cpc_wt/dev1"
```

收工：

```bash
node "00. 仓库管理/租约.mjs" release --agent dev1
```

## 五、端口与路径分配

| 用途 | 端口 | 说明 |
|---|---|---|
| 正式服务 | 3000 | 只有一个人能起，改动期间建议停掉 |
| 验收基线 | 3101–3109 | 测试 agent 专用 |
| 开发自测 | 3110–3119 | 一个 agent 一个，claim 时登记 |
| 临时排查 | 3120+ | 用完即弃 |

DB 副本路径固定为 `<worktree>/_db/data.db`，用 `VACUUM INTO` 生成，
**永远不要指向 `04. 四期/系统代码/data.db`**。

## 六、提交纪律

1. **一个缺陷一个提交**。混在一起，回滚时只能整段退。
2. **push 前先 `git fetch`**。看到远端动了，先 `rebase`，不要 `merge`（会造出无意义的合并提交）。
3. **冲突时不要 `push --force`**。先 `status` 看谁占了这块，问清楚再动。
4. **合并顺序：先小后大**。小的先合，大的 rebase 一次就够；反过来要 rebase 好几次。
5. **不要为了让自己的分支好合，去改对方的代码**。那是掩盖冲突，不是解决冲突。

---

## 七、撞车之后怎么收

已经撞了，按这个顺序：

1. **停手**。两边都不要继续改同一批文件。
2. **列差异**：`git diff <base>..<branch> --stat`，看清各自动了哪些文件。
3. **判断谁的实现更完整**，不是「谁先提交」。看三条：边界情况、是否顺手修了邻接缺陷、有没有测试。
4. **保留测试与断言**，两边都留。实现可以选一个，用例必须都跑。
5. **把落选的实现记进 defects.csv 的备注**，说明为什么没采用 —— 否则下次还会有人重做一遍。

> 这次的实际结论：A 的实现比 D 细（`/api/pick` 分了 strict/scrub/open 三级，
> 还对前线做了「只能看到自己那条员工记录」），C 也比 D 完整（顺手修了 STK-09 调整单编号）。
> 所以归并时应当以 A/B/C 为主，D 只保留测试与文档。

## 八、跨机器怎么办

租约只在同一台机器有效（它是本地文件）。跨机器靠：

- 分支 + PR，不直接推 `main`
- PR 描述里写清「占了哪些域」
- 仓库设 `CODEOWNERS`，让热点文件必须有人 review
- CI 跑 `run-tests`，冲突在语义层也能被测试抓到
