## 1. 文檔目的

本 PRD 把原始業務梳理轉成可設計、可開發、可驗收的需求，供產品、架構、開發、測試及業務代表共同評審。

本文件使用以下約束語：

- **必須**：上線驗收的必要條件。
- **應該**：原則上需要，偏離時必須記錄原因並批准。
- **可以**：可選能力，不影響本期核心閉環。
- **待決策**：業務或財務規則尚未確認，相關模組不得自行假定。

需求編號一經建立不得複用；變更需求時保留原編號並補充修訂記錄。

## 2. 背景與現狀判斷

公司存在四類業務：

1. 商品銷售。
2. 自營滅蟲服務。
3. 承接其他公司外判的滅蟲項目。
4. 清潔外包轉介並收取佣金。

現有系統已具備客戶、報價、訂單、送貨、庫存、排程、工作記錄、發票、收據、賬單、付款、基本權限及審計能力，適合繼續以模組化單體演進，**不需要推倒重寫或改為微服務**。

目前主要差距是：

- O/E/W/A 尚未形成統一、可校驗的跨部門工作流。
- 商品與服務流程有單據能力，但交接、前置條件及異常路徑不完整。
- 外判項目缺少成本歸集與項目盈虧閉環。
- 清潔轉介缺少佣金、外包結算及應收應付聯動。
- 現有四角色不能完整表達 J/H/A/C/K/L 的職責分工。
- 部分會計視圖由交易欄位推定，尚需建立可追溯的過賬與核銷規則。

## 3. 產品目標與非目標

### 3.1 產品目標

| 編號 | 目標 | 驗收衡量 |
|---|---|---|
| OBJ-01 | 四類業務共用統一訂單與工作流底座 | 不再由各頁面自行解釋狀態或交接規則 |
| OBJ-02 | 每張單據可回答「目前狀態、誰處理、下一步是甚麼」 | 狀態、責任角色、負責人、可執行動作均可查 |
| OBJ-03 | 權限由角色、動作、數據範圍及欄位共同決定 | 未授權請求在服務端被拒絕並留審計 |
| OBJ-04 | 外判與轉介可按項目核算收入、成本、佣金及未結餘額 | 項目盈虧可追溯到原始單據與成本明細 |
| OBJ-05 | 財務與庫存操作具備一致性、冪等性及可沖銷性 | 重複提交不重複過賬，已過賬資料不可直接覆寫 |

### 3.2 非目標

本期不包括：

- 完整薪酬計算、強積金或報稅。
- 多公司、多幣種、多倉庫的集團化 ERP。
- 公網開放客戶自助下單。
- 完整財務總賬替代專業會計軟件的所有能力。
- 為追求技術架構而進行全量框架或數據庫遷移。

## 4. 分期範圍

| 階段 | 交付範圍 | 不包含 |
|---|---|---|
| M0 基礎收斂 | 術語、角色權限、狀態機、審計、單號與安全基線 | 新外判頁面 |
| M1 現有業務閉環 | 商品銷售與自營服務的交接、異常及驗收 | 複雜佣金模型 |
| M2 外判項目 | 項目主檔、成本歸集、驗收、項目盈虧 | 自動薪酬核算 |
| M3 清潔轉介 | 轉介單、佣金規則、外包結算、應收應付聯動 | 多級代理分佣 |

後一階段可以復用前一階段能力，但不得跳過 M0 的狀態、權限及審計基礎。

## 5. 術語與業務邊界

| 術語 | 本 PRD 定義 |
|---|---|
| `Party` | 交易對象主檔；同一公司可同時具有客戶、供應商、上游發包方或下游外包商角色 |
| 客戶 PO | 客戶向本公司發出的採購或服務確認依據，是外部憑證 |
| `SalesOrder` | 本公司對客戶的銷售／服務訂單，不等同供應商採購單 |
| `WorkOrder` | 內部執行工單，可包含排程、人員、物料、報告及驗收 |
| `ProcurementOrder` | 本公司向供應商採購貨品或服務的單據 |
| `DeliveryNote` | 貨品交付及簽收依據 |
| `Invoice` | 向客戶開出的應收憑證 |
| `Receipt` | 客戶款項的收款憑證，必須與發票或未分配款項核銷 |
| `Bill` | 供應商或外包商向本公司開出的應付憑證 |
| `Payment` | 本公司對外付款憑證 |
| `Project` | 外判、服務或轉介業務的收入與成本核算單元 |
| `Referral` | 清潔外包轉介交易，記錄客戶、外包商、佣金模式及結算關係 |
| O | 接單／訂單責任域，不是業務狀態 |
| E | 執行／外勤責任域，不是業務狀態 |
| W | 倉儲／庫存責任域，不是業務狀態 |
| A | 會計／收款責任域，不是業務狀態 |

角色代碼必須使用完整前綴，例如 `OPS_DISPATCH`、`ACCOUNTING`，禁止再以單獨 `A` 同時表示工程部與會計責任域。

## 6. 業務類型

`SalesOrder.business_type` 必須使用以下穩定代碼：

- `PRODUCT_SALE`：商品銷售。
- `SELF_SERVICE`：自營滅蟲服務。
- `OUTSOURCED_SERVICE`：承接上游發包方的滅蟲項目。
- `CLEANING_REFERRAL`：清潔外包轉介。

業務類型決定工作流模板、必需單據及成本核算方式。四類業務共用訂單、權限、審計和財務底座，不建立四套互相重複的流程引擎。

## 7. 角色、數據範圍與權限

### 7.1 角色模型

| 業務職責 | 系統角色代碼 | 主要數據範圍 |
|---|---|---|
| 營業部 J | `SALES_J` | 客戶、報價、本人負責訂單 |
| 營業部 H | `SALES_H` | 客戶分流、報價、供應商及行政資料 |
| 工程部 A | `OPS_DISPATCH` | PO／工單、排程、收工作單、外勤收支 |
| 工程部 C | `OPS_REPORT` | 被指派的報告與執行記錄 |
| 倉儲部 K | `WAREHOUSE` | 拾貨、庫存、理貨及相關 PO |
| 會計部 L | `ACCOUNTING` | 發票、收據、收付款、賬單及入賬 |
| 前線技術員 | `FIELD_STAFF` | 本人及被指派工作 |
| 管理層 | `MANAGEMENT` | 全部資料、審批及系統配置 |

現有 `front`、`office`、`accounting`、`management` 必須通過映射遷移，不得直接批量提升權限。實際用戶映射列入 `DEC-006`。

### 7.2 權限判定

每次請求必須依次檢查：

1. 用戶是否已登入且啟用。
2. 是否擁有該動作權限。
3. 是否可訪問該記錄的數據範圍。
4. 是否可讀寫相關欄位。
5. 當前狀態是否允許執行該動作。

任何一步失敗都必須拒絕，不能僅依賴菜單、按鈕或隱藏欄位。

### 7.4 職責分離

- 報價與收款不得由同一普通用戶完成全流程。
- 倉儲人員不得查看成本價或修改採購成本。
- 已過賬單據不得直接編輯或刪除，只能由有權者沖銷。
- 權限變更必須記錄變更前後值、操作人及原因。
- 臨時代理必須有生效及失效時間，到期自動回收。

## 8. 核心領域模型

### 8.1 聚合關係

```text
Party（交易對象）
  └─ SalesOrder（客戶訂單）
      ├─ Project（需要項目核算時）
      │   ├─ WorkOrder / DeliveryNote / Referral
      │   ├─ CostItem（人工、物料、外包費、車輛、其他）
      │   └─ Settlement（外包或佣金結算）
      ├─ Invoice ─ ReceiptAllocation ─ Receipt
      └─ Bill ─ PaymentAllocation ─ Payment
```

### 8.2 必要實體

| 實體 | 關鍵欄位與規則 |
|---|---|
| `Party` / `PartyRole` | `party_id`、名稱、角色、聯絡資料；角色可多選，禁止因同名自動合併 |
| `SalesOrder` | 客戶、業務類型、來源報價、客戶 PO、主狀態、履約狀態、付款狀態、責任角色、版本號 |
| `Project` | 項目編號、訂單、上游／客戶、負責人、幣種、收入、成本、結算狀態 |
| `WorkOrder` | 訂單／項目、排程、執行人、工作內容、物料、報告、驗收狀態 |
| `PickTask` | 訂單、倉庫、明細、應拾／實拾數量、狀態、執行人 |
| `DeliveryNote` | 訂單、送貨明細、送貨人、簽收人、簽收時間、庫存過賬標識 |
| `Referral` | 客戶、外包商、核算模式、客戶金額、外包金額、佣金規則、驗收與結算狀態 |
| `CostItem` | 項目、成本類型、來源單據、數量、單價、金額、發生日、過賬狀態 |
| `Invoice` / `Bill` | 對象、明細、總額、已核銷額、未核銷額、到期日、過賬狀態 |
| `Receipt` / `Payment` | 收付款對象、方式、金額、日期、銀行參考、作廢或沖銷關係 |
| `*Allocation` | 收付款與發票／賬單的多對多核銷記錄，金額必須大於零 |
| `StockLedger` | 產品、數量變化、前後數量、來源單據、過賬時間；禁止直接改寫歷史流水 |
| `WorkflowEvent` | 實體、前狀態、後狀態、動作、前後責任域、操作人、時間、原因 |
| `AuditLog` | 請求、操作者、權限結果、欄位差異、IP、請求 ID、時間 |

所有核心實體必須具有 `id`、`created_at/by`、`updated_at/by`、`version`；財務與庫存記錄另需 `posted_at/by` 或 `voided_at/by`。

### 8.3 現有模型兼容

- 現有 `purchase_orders` 多數承載客戶訂單／履約語義，遷移期必須增加明確 `order_kind`，不得再混入真正的供應商採購單。
- 可以保留物理表名作兼容層，但應用服務必須使用 `SalesOrder` 領域語義。
- 現有客戶與供應商可逐步映射至 `PartyRole`，保留原 ID 與單號。
- JSON 記錄可繼續承載低風險配置資料；訂單狀態、庫存流水、成本、核銷及結算必須逐步結構化並建立約束。

## 9. 狀態機與交接規則

### 9.1 狀態與責任域分離

每張訂單至少保存：

- `business_state`：草稿、已確認、履約中、待驗收、已完成、已關閉、已取消。
- `owner_role`：目前負責處理的角色。
- `assignee_id`：具體負責人，可空但必須能解釋原因。
- `fulfillment_status`：未開始、準備中、部分履約、已履約、已驗收。
- `payment_status`：未開票、未收款、部分收款、已收款、逾期；由財務記錄計算，不允許手改。

業務履約完成與財務結清是兩個維度。使用信用期付款的訂單不得因未收款而阻止履約驗收；是否允許關閉未收訂單由審批規則決定。

### 9.2 通用狀態遷移

| 動作 | 前置條件 | 狀態／責任域變化 | 必須產生的副作用 |
|---|---|---|---|
| 接受報價 | 客戶、明細、金額及有效期有效 | 報價→已接受 | 建立或更新訂單草稿，保留來源快照 |
| 確認訂單 | 客戶 PO 或批准的替代憑證 | 草稿→已確認 | 建立項目（需要時）、鎖定價格快照 |
| O→E | 服務訂單已確認 | 已確認→履約中；owner→E | 建立工單並通知工程 |
| O→W | 商品訂單已確認 | 已確認→準備中；owner→W | 建立拾貨任務並預留庫存 |
| W→E | 拾貨完成或批准部分出貨 | 準備中→待送貨；owner→E | 建立送貨任務，記錄未交數量 |
| 執行完成 | 工作報告／送貨明細完整 | 履約中→待驗收 | 生成待驗收事項 |
| 驗收通過 | 簽收／驗收憑證有效 | 待驗收→已完成 | 允許按規則開票，凍結履約明細 |
| E→A | 達到開票條件 | owner→A | 建立發票草稿或開票任務並通知會計 |
| 財務結清 | 核銷後未收餘額為零 | payment→已收款 | 更新項目未收餘額，不改寫履約狀態 |
| 關閉訂單 | 無未完成任務且符合信用規則 | 已完成→已關閉 | 鎖定訂單，後續只能沖銷或新增調整 |
| 取消 | 無禁止取消的過賬記錄 | →已取消 | 釋放預留、取消待辦；已過賬部分走沖銷 |

### 9.3 狀態服務要求

- `WF-001`：所有遷移必須經統一工作流服務，禁止頁面或通用保存接口直接修改受控狀態。
- `WF-002`：每次遷移必須在同一事務內完成前置校驗、狀態更新、待辦移交、事件及審計寫入。
- `WF-003`：非法遷移返回 `409`，指出目前狀態、所缺條件及可執行動作。
- `WF-004`：命令必須支持冪等鍵；同一請求重複提交不得重複建單、扣庫或收付款。
- `WF-005`：狀態字典、責任域及動作權限使用常量或配置，禁止散落中文字面量。

## 10. 四類業務流程需求

### 10.1 商品銷售 `PRODUCT_SALE`

主流程：

```text
報價 → 客戶 PO／銷售訂單 → 拾貨 → 送貨 → 簽收 → 發票 → 收款核銷 → 入賬
                              ↘ 缺貨時：採購申請 → 供應商採購 → 收貨入庫
```

| 編號 | 必須實現 |
|---|---|
| `PRD-SALE-001` | 報價轉訂單時保留客戶、明細、運費、折扣、價格與付款條款快照 |
| `PRD-SALE-002` | O→W 建立拾貨任務，記錄應拾、實拾、欠貨及替代數量 |
| `PRD-SALE-003` | 支持批准的 partial delivery；每次送貨只扣實際交付數量且只扣一次 |
| `PRD-SALE-004` | 預留庫存在取消、欠貨或不再交付時釋放，禁止可用庫存被重複分配 |
| `PRD-SALE-005` | 客戶簽收後形成驗收憑證；拒收或部分拒收必須生成差異事項 |
| `PRD-SALE-006` | 供應商採購與客戶訂單分開建模，可追溯到補貨來源，但不得共用 PO 語義 |

### 10.2 自營滅蟲服務 `SELF_SERVICE`

主流程：

```text
報價 → 客戶 PO／服務訂單 → 工單 → 排程派工 → 外勤執行
     → 物料消耗／工作報告 → 客戶簽收或驗收 → 發票 → 收款核銷
```

| 編號 | 必須實現 |
|---|---|
| `PRD-SVC-001` | O→E 自動建立工單與工程待辦，記錄服務地點、頻率、工作細則及所需物料 |
| `PRD-SVC-002` | 排程必須檢查人員可用性；改期、改派及取消保留原因與通知記錄 |
| `PRD-SVC-003` | 前線只能提交本人／被指派工作；工程 A 可審核，工程 C 可編制報告但不能越權改金額 |
| `PRD-SVC-004` | 物料消耗必須連到工單與產品，形成庫存流水及項目成本來源 |
| `PRD-SVC-005` | 返工不得覆蓋原報告，必須建立關聯的新執行記錄 |
| `PRD-SVC-006` | 驗收通過後才允許按常規後付款流程開票；預付款或分期規則另行配置 |

### 10.3 承接外判滅蟲項目 `OUTSOURCED_SERVICE`

主流程：

```text
上游發包方接洽 → 項目報價／合約 → 項目與工單 → 執行及成本歸集
              → 驗收 → 開票收款 → 成本結算 → 項目盈虧
```

| 編號 | 必須實現 |
|---|---|
| `PRJ-001` | 建立項目主檔，明確上游發包方、最終服務地點、負責人、合同額及收款條款 |
| `PRJ-002` | 工單、物料、外包費、車輛費及其他直接成本必須帶 `project_id` |
| `PRJ-003` | 成本可由來源單據自動產生或授權錄入；所有成本保留來源與過賬記錄 |
| `PRJ-004` | 項目收入、成本、未收、未付及盈虧必須可追溯到明細，不接受只有手填總數 |
| `PRJ-005` | 項目關閉前列出未驗收工作、未開票收入、未收金額、未結成本及未付款項 |
| `PRJ-006` | 已關閉項目的補充成本只能以調整項記錄，並重新計算盈虧及保留審批 |

項目盈虧口徑：

- 項目收入＝已確認項目收入；報表同時列示合同額、已開票額及已收款額。
- 項目成本＝人工＋物料＋外包費＋車輛＋佣金＋其他直接成本。
- 項目毛利＝項目收入－項目成本。
- 不得把「已收款」誤當「已確認收入」，也不得把「未付款」自動排除在應計成本外。

### 10.4 清潔外包轉介 `CLEANING_REFERRAL`

主流程：

```text
客戶需求 → 轉介單 → 選擇外包商 → 簽約及核算模式 → 外包執行／監督
        → 驗收 → 客戶應收 → 外包商應付／佣金 → 收付款核銷 → 轉介盈虧
```

| 編號 | 必須實現 |
|---|---|
| `REF-001` | 轉介單同時關聯客戶與下游外包商，禁止以文字名稱代替穩定 ID |
| `REF-002` | 每張轉介單必須選擇 `PRINCIPAL_GROSS` 或 `AGENT_NET`，未選不得確認 |
| `REF-003` | 支持固定額、固定比例及固定差額三種佣金規則；規則版本在確認時快照 |
| `REF-004` | 外包執行、監督、驗收及投訴必須有記錄，不能只在備註填寫 |
| `REF-005` | 客戶應收、外包商應付及佣金不得互相覆寫；各自核銷後再計算未結餘額 |
| `REF-006` | 外包商結算必須關聯驗收、賬單及付款，重複賬單或超額付款必須拒絕 |
| `REF-007` | 轉介報表分別列示客戶金額、外包成本、佣金收入、已收、已付及未結餘額 |

核算模式待 `DEC-001` 確認後才能啟用相應會計過賬模板。

## 11. 異常與反向流程

| 場景 | 必須行為 |
|---|---|
| 報價被拒／過期 | 不生成正式訂單；可複製修訂，保留原版本 |
| 報價修改 | 已接受報價不得直接改價，必須建立修訂版並重新確認 |
| 部分拾貨／缺貨 | 記錄欠貨、決定等待／替代／取消，不能只改實拾數後直接結單 |
| 部分送貨／拒收 | 記錄交付與拒收數量，按需建立退回及重新交付任務 |
| 改期／改派 | 保留原排程、變更原因、操作者及通知結果 |
| 返工／驗收失敗 | 回到履約中並建立新執行記錄，不覆蓋原報告 |
| 部分收款 | 生成核銷記錄並更新未收餘額，不得直接改發票已收總數而無來源 |
| 超額收款 | 預設拒絕；如業務需要，轉客戶貸項並經授權，不得靜默丟失差額 |
| 退款／壞賬 | 以獨立憑證及沖銷關係處理，不能刪除原收據或發票 |
| 取消含預留／過賬記錄的訂單 | 先釋放預留；已過賬部分必須沖銷，禁止一鍵物理刪除 |
| 重複提交 | 依冪等鍵返回第一次結果，不重複建單或過賬 |
| 並發編輯 | 版本不一致返回 `409`，要求重新載入並比較差異 |

## 12. 財務、庫存與單號規則

### 12.1 金額與核銷

- `FIN-001`：預設幣種為 HKD；金額使用十進制定點表示，禁止使用浮點累計作財務判等。
- `FIN-002`：單據明細、運費、折扣、稅額及總額的計算順序必須集中定義，報價轉單不得漏項。
- `FIN-003`：發票／賬單與收付款採多對多核銷；任何已收、已付、餘額均由有效核銷記錄計算或一致性更新。
- `FIN-004`：過賬、核銷及沖銷必須在同一事務中完成，並保留來源單據。
- `FIN-005`：已過賬財務記錄不可直接編輯金額；錯誤以沖銷及新憑證修正。
- `FIN-006`：由交易推定的會計視圖必須明確標示為「未過賬推定」，不得與正式憑證混為一談。

### 12.2 庫存

- `STK-001`：可用量＝現存量－有效預留量；出庫時轉實際扣減並釋放相應預留。
- `STK-002`：庫存流水必須保存來源單據、產品、前後數量及操作人。
- `STK-003`：同一來源明細只允許一次有效過賬；缺貨、重複提交或並發操作不得造成負庫存或重複扣減。
- `STK-004`：盤點、送貨、退回及工單耗料共用一致的過賬與沖銷規則。

### 12.3 單號

- `DOC-001`：各單據類型、年度及前綴範圍內單號唯一。
- `DOC-002`：編號必須在事務內原子分配，並以數據庫唯一約束兜底。
- `DOC-003`：轉換、自動生成及手動建立必須走同一編號服務，禁止因缺少欄位鍵而產生空單號。
- `DOC-004`：歷史單號保持不變；補號或重號修復必須有映射及審計。

## 13. 應用服務與模組邊界

保持模組化單體，優先把業務命令從通用 CRUD 中分離：

```text
lib/
  domain/       狀態字典、權限策略、金額與核算規則
  services/     訂單、工單、庫存、項目、轉介、發票與結算命令
  repositories/ 核心實體查詢、約束與事務
  presenters/   頁面與打印輸出，不直接改受控狀態
```

下列命令必須由服務端獨立暴露並執行完整校驗：

- `acceptQuotation`、`confirmSalesOrder`、`releaseOrder`
- `completePick`、`assignDelivery`、`postDelivery`
- `submitServiceReport`、`acceptWork`
- `issueInvoice`、`allocateReceipt`、`allocatePayment`
- `postCostItem`、`closeProject`
- `confirmReferral`、`acceptReferralWork`、`settleReferral`
- `reversePosting`、`cancelOrder`

通用 `/save/:entity` 不得成為繞過上述命令的第二條寫入路徑。

## 14. 安全、審計與隱私

- `SEC-001`：預設拒絕；所有權限在服務端執行，直連路由與選擇器採用相同策略。
- `SEC-002`：金額、成本、聯絡資料等敏感欄位在序列化層裁剪，不能只做視覺隱藏。
- `SEC-003`：所有寫操作保留 CSRF、防重放、輸入校驗及會話檢查。
- `SEC-004`：首次部署不得建立已知固定密碼帳號；初始管理員必須通過安全流程建立並強制改密。
- `SEC-005`：公開代碼倉庫不得包含真實客戶資料、個人資料、附件、令牌、可用密碼或生產數據庫。
- `SEC-006`：審計至少覆蓋登入、查看敏感資料、權限拒絕、狀態遷移、金額變更、過賬、沖銷及權限變更。
- `SEC-007`：審計記錄不得由普通業務用戶修改或刪除；敏感內容按最小必要原則記錄。

## 15. 數據遷移要求

1. 遷移前建立一致性備份並完成恢復演練。
2. 保留原記錄 ID、單號、金額、日期及來源關係。
3. 為現有 `purchase_orders` 補充分類與遷移映射，禁止把全部記錄盲目改名後繼續混用。
4. 客戶／供應商角色映射只增加角色，不擅自合併同名對象。
5. 用戶角色逐人映射並由管理層確認，遷移後默認收回多餘權限。
6. 歷史金額、已收已付及庫存必須做遷移前後總量核對；差異逐筆輸出。
7. 遷移腳本必須可重入，重複執行不得重複生成項目、成本或核銷記錄。

## 17. 核心驗收場景

### AC-01 自營服務正常閉環

- 给定一張已接受服務報價及有效客戶 PO。
- 當營業確認訂單，系統建立工單並把責任域移交 E。
- 當工程完成排程、執行、報告及驗收，系統允許移交 A。
- 當會計開票並完成部分及剩餘收款，系統分別顯示部分收款與已收款，且全部步驟可追溯。

### AC-02 商品部分交付

- 给定訂單數量 10、可用庫存 8。
- 系統不得假裝足量交付；必須顯示缺貨 2 並要求選擇等待、替代或取消。
- 批准交付 8 後只扣減 8，剩餘 2 保留為欠貨或按決定取消。
- 重複提交同一送貨命令不得再次扣庫。

### AC-03 外判項目盈虧

- 给定項目合同額、兩筆物料成本、一筆外包費及一筆車輛費。
- 當成本過賬，項目報表逐筆顯示來源並計算毛利。
- 當外包費尚未支付，成本仍按規則納入項目，同時單獨顯示未付餘額。

### AC-04 轉介總額模式

- 给定 `PRINCIPAL_GROSS`、客戶金額及外包商賬單。
- 系統分別建立應收與應付，收入及外包成本不得互相覆寫。
- 部分收款和部分付款後，報表正確顯示各自未結餘額。

### AC-05 轉介淨額模式

- 给定 `AGENT_NET` 及固定佣金規則。
- 系統按已確認規則計算佣金收入，不把客戶總額自動全額列作本公司收入。
- 規則後續修改不得改寫已確認轉介單的佣金快照。

### AC-06 非法狀態遷移

- 给定未驗收工單，普通用戶嘗試直接標記已關閉。
- 系統返回 `409`，不落庫，指出缺少驗收條件並記錄拒絕事件。

### AC-07 動作與數據權限

- 工程角色可以提交被指派報告，但不能開收據或修改金額。
- 前線直接請求其他員工記錄時被拒絕，即使手動修改 ID 或隱藏欄位也無效。

### AC-08 欄位權限

- 倉儲可查看產品及數量，但列表、詳情、編輯頁、選擇器、匯出均不得取得成本價。
- 管理層查看同一資料時可見完整欄位，訪問行為按規則留審計。

### AC-09 超額與重複核銷

- 當收款超過發票未收餘額，預設拒絕且發票、收據及核銷均不改變。
- 當同一收款命令以同一冪等鍵重試，只返回首次結果，不增加已收金額。

### AC-10 已過賬沖銷

- 已過賬送貨或收款不得直接刪除。
- 有權者執行沖銷後產生反向記錄，原記錄、反向記錄及庫存／財務餘額可互相追溯。

### AC-11 取消與預留釋放

- 商品訂單取消後，未交付預留被釋放。
- 若已有有效過賬，系統要求先完成相應沖銷，不允許只改狀態為已取消。

### AC-12 遷移一致性

- 遷移前後單據數量、金額、庫存、已收已付及原 ID 對賬一致。
- 重複執行遷移腳本不增加記錄，不產生重號或重複成本。

## 18. 完成定義（Definition of Done）

每項需求只有同時滿足以下條件才算完成：

- 服務端動作、數據及欄位權限均已實現。
- 狀態前置條件、異常路徑及冪等行為已實現。
- 相關操作具備事務、審計及可追溯來源。
- 遷移與兼容策略不影響歷史金額及單號。
- 至少覆蓋一個正常、一個邊界及一個越權／異常驗收場景。
- 不使用「頁面能打開」或「HTTP 302」代替業務結果驗證。
- 文檔、狀態字典、角色映射及缺陷台賬同步更新。

## 19. 待業務決策項

| 編號 | 必須決策的問題 | 阻斷範圍 |
